# Continuous improvement for court operations

**Direction:** Albert Tan Sin Hon, 1 November 2026.
**Action:** `CSI-CONT-20261101-1`. **Status:** maintenance configured; benefits unmeasured.

## Purpose and ownership

Develop useful submission-review workflows for filers, court registries and
judicial reviewers. Improvement means fewer avoidable defects and less total
human work without impairing access to justice, not merely more features or flags.
The canonical implementation is this dedicated repository. The earlier profile-
repository folder is historical provenance, not a parallel development tree.

The existing Academic GitHub Development task owns implementation. Its daily
flexible morning schedule in Asia/Singapore is unchanged. Each occurrence checks
current code, open work, failures, authorised feedback and the next evidence gate.
Wednesday's existing occurrence includes a substantive court-operations checkpoint
and a concise report, including a reasoned no-change or deferral result when needed.
The first Wednesday checkpoint is 4 November 2026. This adds no second scheduler
and does not promise a code change on every run. Shared engineering capacity,
protected portfolio obligations and existing authority boundaries remain in force.

## The repeatable development cycle

1. **Identify an evidenced task.** Name the user, court/jurisdiction, proceeding,
   document type and operational difficulty. Use current primary rules, directions,
   judgments, filing specifications, institutional reports or authorised first-hand
   feedback. Record source URLs, pinpoints, versions and dates. Distinguish a public
   concern, an inferred need, requested testing and a confirmed adoption decision.
2. **Establish the baseline.** State the current revision, supported input, manual
   alternative, acceptance measure, negative examples and stop criterion. Reproduce
   a defect or record a concrete workflow obstacle before choosing a change.
3. **Complete one bounded slice.** Resume existing work; use a focused branch,
   implementation/tests/documentation together, full-diff review, exact-revision
   checks and a guarded merge. Recheck a changed base or head. Preserve failed tests
   and uncertainty; an absent or skipped check is not a pass.
4. **Evaluate the whole workflow.** Use independently labelled, permitted held-out
   examples and an authorised non-implementing reviewer. Disclose role, interests
   and assistance. Agent review does not satisfy this gate. Record unavailable
   independent evaluation as blocked, while continuing safe internal preparation.
5. **Retain, revise, defer or stop.** Record the comparison, remaining limitation,
   next owner/action and review date in [PROGRESS.md](PROGRESS.md). Keep private
   materials in the existing private archive. A deferral needs a reason and next
   review; surface three successive eligible deferrals rather than losing the work.

## What to improve first

Finish publication and real defects before speculative features. The next product
gate is one permitted authoritative-source resolver with citation identity, dated
retrieval provenance, source version, exact pinpoints and explicit unavailable or
ambiguous results. No source unavailability may be relabelled as fabrication.

Then strengthen quotation/evidence checks, the correction-and-explanation workflow
and independently evaluated source-grounded reasoning assistance. Separate
production/discovery responses from written legal submissions and evidential
statements. Apply one validated court and document-type profile at a time.
Court-specific integration is a later authorised shadow-pilot stage, not an
assumption that every filing platform exposes a compatible API.

## Operational outcome measures

| Measure | Evidence needed |
| --- | --- |
| Source and pinpoint coverage | Defined eligible references, successfully resolved references and explicit unavailable/ambiguous cases |
| False alarms and missed defects | Independent reference labels, per-defect denominators, precision/recall and retained reviewer disagreement |
| Extraction and abstention | Failed/partial documents, unsupported formats/languages and unresolved findings, not silently excluded cases |
| Correction and rework | Whether a finding produced a justified correction, explanation, escalation or unnecessary work |
| Total human effort | Setup, annotation, filer correction, registry handling, judicial review, false-alarm checking and support |
| Reliability and safety | Reproducible failure recovery, source-version handling, confidentiality and independently assessed controls |

Set pilot acceptance thresholds before viewing held-out results with the authorised
evaluator or court partner; none are agreed yet. Compare with ordinary manual
review, not just the previous software test count. Do not claim backlog reduction
from a small internal exercise. A faster engine can still increase total human work.
No independent accuracy, court-time saving, adoption or commercial demand is yet
established.

## Boundaries that every improvement must preserve

Keep original submissions and source versions distinct from annotations. Preserve
opposing accounts, legitimate alternative pleadings, legal novelty and disputed
facts. Evaluate self-represented writing, translation and extraction limitations
without using prose polish as a proxy for truth. No automated filing rejection,
delay, sanction, credibility score, merits decision or truth certificate.

No new expenditure, paid model/API, metered hosting or hosted CI is authorised by
this protocol. Verify an authorised resource envelope before such operations.
Reserved rights, private archives, sealed/privileged information and source licences
remain protected. Actual case processing, authenticated integration and court
outreach need their separate authority and evidence. Maintain the safeguards in
[THREAT_MODEL.md](THREAT_MODEL.md) and the staged [GLOBAL_ROADMAP.md](GLOBAL_ROADMAP.md).

## Reporting

Each meaningful receipt identifies the problem, source/baseline, exact revision and
PR, checks actually run, review type, observed result, remaining uncertainty and
next owner/gate. Separate configured, attempted, committed, merged, released,
deployed, independently used and outcome measured. The recurring configuration
itself is not evidence that any future review, improvement or efficiency gain
has occurred. Costs and human effort remain unknown unless actually recorded.
